# 多会话并行调度手册

这份手册解决一个常见问题：多个 IDE 对话、多个子代理同时操作同一个仓库时，
怎样让团队保持并行效率，又不会互相覆盖、丢失上下文或把未验收任务抛在一边。

核心结论是：**多会话之间不靠聊天记忆协调，而靠文件和调度员协调。**
每个会话只保留一个当前任务；需求、边界、结果和风险都写进工单。

## 1. 适合的场景

- 同一仓库有多个可并行的功能、修复或排查任务。
- 前端、后端、测试、文档和视觉验收有不同节奏。
- 用户不断提出新想法，但已有任务还不能中途丢下。
- 实现代理由不同模型或不同 IDE 承接，需要统一验收。

不适合把强依赖任务强行并行。如果两个任务的输入来自同一个文件、同一张表、
同一个接口契约或同一个状态机，先把依赖拆开，或改成顺序执行。

## 2. 三条硬规则

1. **未验收任务优先收尾。**
   当前任务处于实现、测试或等待验收状态时，不因新需求自动切换。新需求一律另建工单进入队列。
2. **每个活跃工单有唯一文件边界。**
   两个代理不得同时编辑同一文件。共享契约文件先冻结，只允许一个代理修改。
3. **调度员统一入队、合并和验收。**
   会话可以并行，调度员负责检查边界、汇总交付、跑验证并决定返工或验收。

只有在用户明确要求暂停、取消或切换时，才可以中断未验收任务。切换时必须在原工单记录当前状态、剩余步骤和恢复入口。

## 3. 队列与状态

建议每个工单至少记录以下状态之一：

| 状态 | 含义 |
| --- | --- |
| `queued` | 已建单，等待文件边界检查和派发 |
| `dispatched` | 已派给实现代理或外部模型 |
| `review` | 已返回交付，等待独立验收 |
| `rework` | 验收失败，返工次数未超过上限 |
| `blocked` | 缺少信息、环境或用户决策 |
| `accepted` | 验收通过，可关闭 |

每个会话同一时间只处理一个 `dispatched` 或 `review` 状态的任务。
用户新增的想法不能直接打断当前执行，先转成 `queued` 工单。
`blocked` 不算完成；必须写清缺什么、等谁、恢复条件是什么。

## 4. 派单前检查清单

调度员派单前逐项确认：

- 目标是否一句话说得清？
- 项目路径、工单路径、必要文件列表是否齐全？
- 允许修改和不允许修改的文件是否分开写？
- 是否有共享契约文件？它是否已经冻结？
- 活跃工单中有没有文件边界重叠？
- 完成条件是否能用命令、测试、退出码或明确截图判定？
- 并行任务数量是否低于配置的并行上限？
- 模型分配是否写进工单？

任何一项不成立，先拆任务或补工单，不要让代理自行猜边界。

## 5. 文件边界登记表

并行前维护一张简短的边界表。它可以直接写在调度工单里：

```markdown
| 工单 | 允许修改 | 禁止修改 | 交付判定 |
| --- | --- | --- | --- |
| W1 | `app/api/orders.py`, `tests/test_orders.py` | `app/api/schema.py` | `pytest tests/test_orders.py` |
| W2 | `app/web/OrderTable.vue`, `tests/order-table.spec.ts` | `app/api/**` | `npm run test -- order-table` |
```

规则：

- 契约文件、类型定义、数据库迁移、路由注册表、全局配置属于高冲突区。
- 这些文件需要变更时，先单独开前置工单；完成后冻结，再派实现任务。
- 检查到边界重叠时，选择合并为一个工单、串行执行，或把共享部分抽出成独立前置任务。
- 实现代理只能修改“允许修改”里的文件；发现必须改其他文件时，停下来回报，不自行扩范围。

## 6. 最小上下文和紧凑交付

给实现代理的输入只需要：

```text
工单路径
项目路径
允许修改范围
必要文件列表
完成条件
实际使用模型
```

代理返回只需要：

```text
修改文件列表
测试结果
遗留风险
```

不要转发完整聊天记录，不要让代理在聊天里重复输出完整文件或完整差异。
编译、单元测试、文件存在性、接口探活等确定性检查用工具执行，不用模型复述来判断。

## 7. 模型路由模式

不要只按角色固定模型，按任务性质路由模型：

| 任务类型 | 建议路由 | 说明 |
| --- | --- | --- |
| 大量代码读取、批量扫描、日志分析、批量生成 | `cheap_code` | 控制成本，只传工单和文件清单 |
| 架构设计、关键业务逻辑、复杂联调 | `stable_logic` | 优先稳定性和可维护性 |
| 截图走查、图表渲染检查、UI 视觉验收 | `vision` | 多模态结果更可靠 |
| 任务拆解、工单管理、跨会话调度、最终验收 | orchestrator | 需要全局上下文 |

`cheap_code`、`stable_logic` 和 `vision` 是逻辑槽位，不是固定字段；
可在模型路由表或 `LLM配置.json` 的模型池中映射到当前可用的具体模型。

并行实现时的默认约束：

- AgentB 和 AgentD 并行时，默认不共用同一个实现模型。
- 如果只能使用同一模型，必须保证文件边界完全隔离，并在工单中记录该限制。
- 外部 API 超时、错误或不可用时，结果标记失败并回退内置执行；调度员重新决策，不把失败回复当作验收结果。
- 每张工单写清实际模型，便于事后定位质量差异和成本。

## 8. 返工与止损

验收失败时，按顺序判断：

1. 修复成本低于重做成本：派回原代理，附带具体缺陷和验证命令。
2. 上下文已被污染或连续失败：新建干净工单，只携带结论和复现步骤。
3. 连续返工达到上限（建议 2 轮）：调度员停止自动重试，向用户汇报证据、选项和建议。
4. 连续 3 次失败：必须停止派单，等待用户决策，不得静默换路线。

降级不是失败，但必须透明。报告中要说明实际执行者、是否缺少独立上下文隔离、
哪些检查未执行。没有真实交付时，不能写成某个实现代理已完成。

## 9. 每轮收尾记录

每个任务关闭前，把可复用的信息写回工单或经验记录：

```markdown
## 执行记录
- 派单时间：
- 实际模型：
- 文件边界：
- 测试命令：
- 结果：

## 结论
- 已完成：
- 未验证：
- 下一步：
```

只保留稳定、可复用的经验，不记录密钥、业务源码、原始日志、内部地址和个人数据。

## 10. 一页速查

1. 未验收任务先收尾，新需求只入队。
2. 多会话协调靠工单文件，不靠聊天记忆。
3. 派单前扫文件边界，重叠就不并行。
4. 共享契约先冻结，再派实现任务。
5. 每个工单写清模型、范围、完成条件和验证命令。
6. 代理只收最小上下文，只回修改文件、测试结果和风险。
7. 并行实现默认错开模型，失败显式降级。
8. 最多自动返工 2 轮，之后停下来问用户。
