# 我不再用 AI 聊天写代码了——我搭了一支 AI 工程团队

> 开源地址：[davececec/Portable-AI-Team](https://github.com/davececec/Portable-AI-Team)
> 纯标准库 Python，单文件夹，支持 5 个 IDE，复制即用。

市面上 99% 的 AI 编码工具有同一个结构性缺陷：**同一个模型写完代码，然后自己说"做完了"。**

写代码的是它，验收的还是它。你让它"检查一下你的工作"，它把自己的输出总结一遍，告诉你没问题。

这不是工程，这是自我表扬。

所以我换了一种做法：把 AI 当成一支真正的工程团队来管——写代码的和验收的是不同角色，派单用工单不用聊天记录，模型按任务路由而不是一把梭，经验是文件不是会话。

这套东西我在一个真实的工业能源管理系统项目上跑了两个月。下面是我踩过坑之后，觉得真正值得说的东西。

## 第一条铁律：写代码的不许验收

我的团队里有一个角色叫 AgentB（实现），一个叫 AgentA（调度 + 验收）。

AgentB 交活的时候必须带**证据**：跑了哪些测试、探了哪些接口、浏览器走了哪些页面、截图有哪些。AgentA 收到后独立做确定性检查——编译、单测、退出码、文件存在性——全过了才标"已交付"。

没有证据，不算交付。

**一个真实案例说明这条铁律有多值钱：**

我在一个六阶段的能源监控项目里，让 AgentB 写了一个排名图表，渲染在一个 `v-if` 控制的容器里。用户切换分析周期的时候，Vue 把 DOM 节点销毁了，图表直接空白，再也回不来。

AgentB 测试过图表"能显示"，所以它报告成功。

但团队的视觉验收 Agent——一个完全独立的视觉模型，不在主对话里跑——在真实渲染的页面上跨三个断点走查，看到了空白图表，给出了根因分析（`v-if` 卸载导致 ECharts 实例丢失），还提了三个修复方向。

写代码的那个 Agent 永远不会发现自己的遗漏，因为它没像用户那样盯着屏幕看。

这就是"实现与验收分离"的全部商业价值，一页 PPT 讲得完。

## 派单不发聊天记录，发工单

多 Agent 场景里最大的 token 浪费是把整段对话转发给子 Agent。我不这么干。

AgentA 派活给 AgentB/AgentD 时，只给五样东西：

1. 工单文件路径
2. 项目路径
3. 允许修改的文件范围
4. 实际需要的文件清单
5. 验收条件

没有聊天历史。AgentB 干完只返回：改了哪些文件、测试结果、遗留风险。不返回完整代码，不复述对话。

这不是优化，这是让并行成为可能的前提。两个 Agent 在同一个仓库里干活，互相不会踩对方的上下文；人聊了多长，token 账单都不会跟着涨。

## 模型路由：把"锁定"这个顾虑拆掉

我不用一个模型打天下。每个任务按性质路由到合适的模型，路由表是你自己的一个文件：

| 任务类型 | 路由到 | 原因 |
|---|---|---|
| 日常编码 | 便宜快的模型 | 高频低成本 |
| 架构 / 关键业务逻辑 | 强模型 | 硬骨头值得花钱 |
| 批量读文件 / 日志排查 | 便宜快的模型 | 体力活 |
| 截图 / 图表视觉验收 | 视觉模型 | 图像读取稳 |
| 并行第二实现者 | 和第一个**不同**的模型 | 相同模型会犯相同的错 |

最后一行是大多数人想不到的。两个 Agent 并行干活时，我故意给他们不同的模型——因为同一个模型遇到同一个模糊需求，会自信地写出同一个错误答案。脑子不一样的实现者才是真正的交叉检查。

因为路由表就是一个文件，采购决策者最怕的两个问题直接消失：

- **模型涨价了？** 改一行配置，不锁供应商定价。
- **要换 IDE？** 换 adapter。团队、规则、经验、验收纪律跟着文件夹走。

我目前在一个文件夹里跑了五个平台：Codex、Google Antigravity、TraeCode、Claude Code、WorkBuddy。后两个在文档里明确标了"未官方验证"——我宁可告诉你我还没验证过什么，也不让你以为我全验证过了。

## 失败是一等公民

所有"健壮 AI 系统"的文章都默认模型很乖。我的模型不乖，所以我定了三条纪律：

1. **探针只打一次。** 不可用就判定环境限制并降级，不盲目重试三次然后卡死。
2. **外部调用失败不算结果。** 降级到内置模型，AgentA 必须重新决策，不能把外部模型的残缺回复当验收通过。
3. **三次失败就停。** 同一个任务失败两次可以换模型或换角色；三次直接停止派单，报告给人，等人拍板。

还有一条诚实规则：如果某个平台没有真正的子 Agent 隔离，团队会在工单和最终回复里明说"顺序降级：角色模拟"，列出每个角色实际用的模型、上下文隔离是真是假、哪些没验证。AgentB 没交活，就不能写"AgentB 已完成"。

信任不是在做得最好的时候建立的，是在做错之后怎么发现、怎么改的时候建立的。

## 记忆会复利

"调个 API 的工具"和"一支团队"最本质的区别是：**团队用得越久越值钱，工具不会。**

每次任务验收通过后，AgentA 会顺手检查（不额外调模型）这次有没有出现新的、稳定可复用的东西：

- 新的用户偏好？→ 写进 `user-preferences.md`
- 踩了新坑或找到可复用排障路径？→ 写进 `defect-patterns.md` / `effective-solutions.md`
- 确认了架构或数据口径决策？→ 写进 `technical-decisions.md`
- 里程碑？→ 写进 `project-history.md`

四个都不是就什么都不写。只沉淀稳定结论，每条目标不超 300 字，每类文件不超 40 条 / 8000 字。上限到了不删不改旧记忆，原文保留不动，新结论溢出写到 `memory/attachments/YYYY-MM-DD-主题.md` 附件文件，`index.md` 加一条轻量指针。不确定是不是重复或怎么归类时，保留原文并标记待核对。**保真比整洁更重要。**

用一个月，团队记住了你的路由偏好和 UI 规范。用三个月，它记住了你的缺陷模式和建表决策。用一年，它等于一个真的在你系统上干过活的工程师——而且这份经验**跟着文件夹走**，复制到新项目就能用。

原始 API 调用没有这条曲线。

## 这不是什么

- 不是加了几个步骤的聊天机器人。
- 不是宣称某个模型最好。它是一套路由**策略**。
- 不是所有平台都完美。五个里两个明确标了未验证。
- 不是魔法省钱。它是让上下文和重试有边界的**纪律**。
